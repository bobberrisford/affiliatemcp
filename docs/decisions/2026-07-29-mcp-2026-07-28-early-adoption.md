## Context

On 2026-07-28 the Model Context Protocol finalised its largest revision since
launch. The core protocol becomes stateless: the `initialize`/`initialized`
handshake and the `Mcp-Session-Id` header are removed for Streamable HTTP,
every request is self-contained (client info moves to `_meta`), routing gains
required `Mcp-Method` and `Mcp-Name` headers, upfront capability discovery
moves to a new `server/discover` request, long-lived SSE streams are replaced
by multi round-trip requests (`InputRequiredResult`), and results may carry
`ttlMs` and `cacheScope` caching metadata. A formal extensions framework
(reverse-DNS identifiers, independent versioning) ships alongside, with Tasks
and MCP Apps as the first official extensions. The revision is breaking; there
is no in-protocol compatibility bridge.

Where this repository stands, verified on 2026-07-29:

- The **local stdio server**, the primary product, is unaffected. The
  stateless rework targets Streamable HTTP. Nothing in `src/server.ts` or the
  adapter fleet needs to change.
- The **hosted connector is live and charging** at `mcp.agenticaffiliate.ai`
  (#427), built on exactly the shape the new spec removes:
  `src/hosted-transport/http-server.ts` keys a per-session `Server`/transport
  pair on `mcp-session-id`, mints sessions on `initialize`, and holds SSE GET
  connections. Live clients (Claude custom connectors) speak the old
  revision today and must keep working.
- The **TypeScript SDK does not support the new revision**. The newest
  release, 1.30.0 (published 2026-07-27), tops out at
  `LATEST_PROTOCOL_VERSION = '2025-11-25'`, and npm has no pre-release
  channel. Every server that waits for the SDK cannot ship 2026-07-28
  support today.
- The **official conformance suite already tests the new revision**.
  `@modelcontextprotocol/conformance` `0.2.0-alpha.10` (published 2026-07-27)
  contains scenarios for `Mcp-Method` routing, `server/discover`, and
  stateless behaviour.

That combination is the opening: the acceptance harness for the new spec
exists, the mainstream implementation path (the SDK) does not, and our hosted
dispatch is already stateless where it matters. Per-request bearer auth
(`call-context.ts`), per-call vault credential resolution (`dispatch.ts`),
the tier gate, and the meter all operate per request; the session map is SDK
plumbing, not load-bearing state. A thin stateless HTTP layer over the
existing dispatch is a small, honest amount of work, not a rewrite.

## Decision

Adopt the 2026-07-28 revision early on the hosted connector, additively, with
the official conformance suite as the only arbiter of the claim "supported".

1. **Dual-stack, zero downtime.** The existing sessionful Streamable HTTP
   endpoint stays exactly as it is for current clients. A new stateless
   handler implementing the 2026-07-28 core (self-contained requests,
   `Mcp-Method`/`Mcp-Name` routing, `server/discover`, no session header, no
   long-lived SSE) is added beside it. Requests are routed by protocol
   signals: presence of `Mcp-Method` headers selects the stateless path;
   `initialize` bodies and `mcp-session-id` headers select the legacy path.
   Neither path knows the other exists.

2. **Hand-roll the thin layer; do not fork the SDK.** The stateless handler
   is a small amount of repository-owned code over the existing dispatch
   seam (`dispatch.ts`, `tier-gate.ts`, `rate-limiter.ts`, `audit.ts`), using
   the SDK's types where they exist and plain typed JSON-RPC where they do
   not. The local stdio server stays on the official SDK untouched. When the
   SDK ships 2026-07-28 support, the hand-rolled handler is replaced by the
   SDK implementation and deleted; that replacement is a named follow-up,
   not an option.

3. **Conformance is the definition of done.** "Supports MCP 2026-07-28"
   may be claimed only while the official conformance scenarios for the
   stateless core pass in CI against the hosted endpoint. The suite is
   pinned per run but tracked: an alpha-to-final scenario change that breaks
   us is treated as our bug until proven otherwise.

4. **Custody and entitlement posture is unchanged.** The stateless path
   reuses the same per-request bearer auth, vault lookup, tier gate, meter,
   and audit line as the legacy path. No new state is introduced anywhere;
   this change removes state, it does not move it.

5. **No extensions yet.** Tasks and MCP Apps are attractive (product feed
   downloads and setup flows respectively) but each needs its own decision
   record anchored to a concrete user outcome. This record authorises the
   stateless core only.

6. **The public claim goes through the reviewed marketing lane.** Any
   "among the first MCP servers on the new spec" content is prepared under
   campaign mode (2026-07-27 record), grounded in the passing conformance
   run, phrased matter-of-factly, and approved by Rob before publication.

## Rejected alternatives

- **Wait for the TypeScript SDK.** Safest, and the default we already
  recorded in the initial assessment. Rejected as the primary path because
  it forfeits the entire first-mover window: no SDK release or pre-release
  supports the revision, and every competitor on the SDK is equally stuck.
  The SDK remains the destination; we simply refuse to idle until it ships.
- **Cut the hosted endpoint over to stateless-only.** Simplest end state,
  but it breaks every live paying client today, since no mainstream client
  speaks 2026-07-28 yet. Rejected outright; the hosted tier is charging.
- **Fork or patch the SDK to add the revision.** Far more surface than we
  need, an ongoing rebase burden, and it couples our transport to code we
  do not own. The thin handler over our own dispatch is smaller than a fork.
- **Claim support from documentation alone.** Cheapest, and dishonest. The
  project's register is verifiable claims; the conformance suite exists, so
  it is the bar.

## Consequences and accepted risks

- **Temporary owned transport code.** The hand-rolled handler is real debt
  with a named deletion trigger (SDK support lands). It is confined to
  `src/hosted-transport/`, behind the existing typed dispatch contract, and
  never touches `src/shared/`.
- **Spec drift.** The suite we test against is an alpha. Scenarios may churn
  between now and the suite's stable release. Mitigation: pin the suite
  version, re-run on each suite release, and treat the claim as suspended
  whenever the pinned-to-latest delta fails.
- **Zero-client window.** The stateless endpoint may have no compatible
  mainstream client for weeks. Accepted: the point is readiness, a tested
  head start, and a credible verifiable claim, not immediate traffic.
- **Live-surface risk.** The legacy path serves paying users; the new path
  must not degrade it. Mitigation: additive routing only, no shared mutable
  state, the existing hosted smoke tests must stay green, and the stateless
  path ships behind an environment flag until the conformance run is green
  in CI.

## Workstream brief

**User outcome.** An affiliate professional whose MCP client adopts the
2026-07-28 revision can point it at `mcp.agenticaffiliate.ai` on day one and
run the same reports as today, with the same custody guarantees; and the
project can honestly state it was among the first servers to support the
revision.

**Dependency graph.**

```
PR-A (this decision, docs-only)
  └─ PR-B conformance baseline (routine lane)
       └─ PR-C stateless handler + proof (active-risk lane, needs PR-A accepted)
            └─ PR-D docs + claim + findings (routine lane)
```

**Owning domains.** PR-B: dev tooling and CI. PR-C: `src/hosted-transport/`
plus its tests. PR-D: README, `docs/findings/`, client-support table. No PR
touches `src/shared/`, adapters, or the stdio server.

**Per-PR acceptance proof.**

- **PR-A (this PR):** docs-only diff; Rob's explicit acceptance recorded in
  this file's status line before PR-C starts.
- **PR-B:** SDK bumped 1.29.0 to 1.30.0 with a green baseline (`npm run
  verify`); `@modelcontextprotocol/conformance` added as a dev dependency
  with an `npm run conformance:hosted` script; the subset of scenarios the
  current legacy endpoint should pass, passing, recorded as the baseline.
  Routine: no public contract changes, decision-complete.
- **PR-C:** the stateless handler, unit tests beside it, and the official
  2026-07-28 stateless scenarios green in CI against a locally started
  hosted transport; legacy-path smoke tests unchanged and green; complete
  diff inspected; independent agent review plus green CI as the risk
  backstop, then Rob's deliberate merge decision.
- **PR-D:** README client table row and findings entry stating exactly what
  passes and against which suite version; campaign-mode marketing drafts
  prepared separately, never inside this PR.

**Stop conditions.**

- The final conformance suite diverges from the alpha such that the handler
  needs a redesign rather than fixes: stop, re-read the spec, amend this
  record.
- The TypeScript SDK ships 2026-07-28 support before PR-C merges: stop
  hand-rolling, switch PR-C to the SDK implementation, keep the same
  acceptance proof.
- Any regression on the legacy hosted path attributable to PR-C: revert
  first, diagnose second.

**Monitoring.** Until the SDK ships support, check `@modelcontextprotocol/sdk`
and `@modelcontextprotocol/conformance` releases weekly and record material
changes against this record.
